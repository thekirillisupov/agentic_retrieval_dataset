# План улучшения качества синтетических вопросов SID (по итогам ревью out_sid_zakupki_tiny_v3)

Ревью запуска:

```
python3 run_sid.py all --config config_sid_zakupki.yaml \
    --corpus data/zakupki/zakupki_tiny.jsonl \
    --meta data/zakupki/zakupki_tiny_meta.jsonl \
    --out-dir out_sid/out_sid_zakupki_tiny_v3
```

Итог ревью: 93 задачи (74 train / 18 holdout). Сплит чистый (0 пересечений по
gold-документам и подграфам, 0 дублей gold-сетов), минимизация и изоляция
отработали. Но в пуле есть системные дефекты, из-за которых holdout в текущем
виде непригоден для валидации, а train даст шумный reward без механической
перепроверки ответов. План ниже упорядочен по отдаче: P0 закрывает ложное
золото, P1 — качество формулировок и разметки, P2 — профиль сложности и
масштаб.

Базовые цифры этого запуска (используются как baseline в критериях приёмки)
лежат в `out_sid_test/out_sid_zakupki_tiny_v3/stats.json`.

---

## P0 — ложное золото и неверные ответы (блокирует обучение)

### P0.1 Completeness для всех механик с выбором из множества

**Проблема.** Проверка полноты множества (`arqg/sid/completeness.py`)
включена только для `set_aggregation` и `constraint_intersection` — 21 задача
из 93. Остальные 72 задачи («какая из двух закупок…», «какая из закупок … была
размещена позже?») уникальны только внутри своего подграфа: среди 25 240 чанков
индекса третью подходящую закупку никто не искал. Изоляция (S7) видит только
top-10 выдачи. Симптом уже в данных: вопрос «какая (ед.ч.) из закупок по
информбезопасности… проводилась не во Владимирской области?» имеет ответ из
двух регионов.

**Действия.**
- В `config_sid_zakupki.yaml` → `completeness.mechanics` добавить
  `comparison`, `temporal_resolution`, `disambiguation_first`, `entity_chain`.
- Для этих механик семантика проверки другая: не «золото = вся истина», а
  «под фильтр вопроса попадают ровно N gold-документов» (для «какая из двух» —
  ровно 2, `n_excess == 0`). Ветку `augment` для них не включать — расширение
  золота меняет смысл вопроса; излишек → repair (ужесточение вопроса) → отсев.
- Композитор для этих механик обязан вернуть структурированный фильтр
  (`require_filter: true` уже есть — распространить требование).

**Приёмка.** Доля задач с `provenance.completeness.status == None` → 0%
(в v3: 72/93). Ручная проверка 20 случайных comparison-задач: пресуппозиция
«двух» подтверждается фильтром по всей мете.

### P0.2 Механическая пересборка ответов из меты

**Проблема.** Ответы пишет генератор, проверяет judge той же модели — и
пропускает ошибки: самопротиворечивый ответ («Цена выросла с 236 567,60 руб.
до 14 560,00 руб.»); ответ-бакет «от 1 до 10 млн руб.» на вопрос о точной цене
(3 задачи — утёк фасет `price_bucket`); ответ, не называющий сущность, когда
вопрос спрашивает «какая… и какова цена».

**Действия.**
- Если `answer_field` числовой/датовый/категориальный из меты — пересобирать
  ответ механически (ветка `answer_rebuilt` в completeness.augment уже это
  умеет; сделать обязательным для всех задач с заявленным фильтром).
- Запретить `price_bucket` как `answer_field`: это бакет, не значение. Точная
  НМЦК берётся из `price_start`. Если вопрос спрашивает цену, а в чанке есть
  только бакет — repair вопроса («в какой ценовой категории…») или отсев.
- Арифметика в ответах («на сколько рублей…», «на сколько дней…») — считать
  скриптом из меты, не доверять LLM; несовпадение с ответом генератора → отсев.
- Канонизировать формат: даты — «D месяц YYYY года», суммы — «1 234 567,89
  руб.»; в задачу добавить поле `answer_aliases` (ISO-дата, число без
  пробелов) для exact-match валидации. В v3 форматы смешаны
  («2019-05-31» vs «26 декабря 2019 года», «13609232.34» vs «1 263 439,85»).
- Если вопрос спрашивает «какая закупка … и какова X» — ответ обязан называть
  сущность, не только X (проверка в G_SOLVE или регэксп-линтером перед ним).

**Приёмка.** Скрипт-аудит (см. P0.4) находит 0 расхождений «ответ vs мета»
на полном пуле; 0 ответов-бакетов на вопросы о точной цене.

### P0.3 Развести generator и judge, включить dual_critic

**Проблема.** Генератор и judge — один и тот же Qwen (self-bias),
`gates.dual_critic: false`, счётчик disagreement за весь запуск = 0 вызовов.
Все дефекты из P0.2 прошли G_SOLVE.

**Действия.**
- Judge — другая модель (или как минимум `dual_critic: true` +
  `drop_on_disagreement: true`; инфраструктура в `arqg/sid/gates.py::g_solve`
  уже есть).
- В G_SOLVE добавить проверку внутренней консистентности ответа (не содержит
  взаимоисключающих утверждений) и соответствия типу вопроса (дата ↔ дата,
  сумма ↔ сумма).

**Приёмка.** `stats.json → gates.dual_critic.calls > 0`,
`disagreement_rate` измерен; на выборке 30 задач ручная проверка ответов не
находит фактических ошибок.

### P0.4 Скрипт-аудит существующего пула (быстрый выигрыш без перегенерации)

Пока P0.1–P0.3 не внедрены, train-часть v3 можно очистить скриптом
(`scripts/audit_sid_answers.py`):
- сверить каждый ответ с метой gold-документов (даты, суммы, регионы,
  номера);
- пересчитать арифметику «на сколько…»;
- прогнать фильтры comparison-вопросов по всей мете и пометить задачи с
  `n_excess > 0`;
- выбросить/пометить задачи с ответом-бакетом и с противоречивым текстом
  ответа.

Выход — `tasks_audited.jsonl` + отчёт с причинами отсева.

## P1 — разметка, разнообразие, естественность формулировок

### P1.1 Метки механик соответствуют вопросу

**Проблема.** ~16% меток врут: 10 задач `comparison` на деле про порядок дат,
5 задач `temporal_resolution` — про сравнение цен. Разрезы по механикам в
`stats.json` шумные, балансировка датамикса по ним — тоже.

**Действия.**
- В промпт композитора — жёсткое определение механики с контрпримерами
  («сравнение дат размещения — это temporal_resolution, а не comparison»).
- В G_SOLVE добавить вопрос judge: «соответствует ли вопрос заявленной
  механике?» → несоответствие = отсев или переразметка.
- Пост-хок правило-классификатор (регэкспы «раньше/позже/первой» vs
  «выше/ниже/дороже») как дешёвый линтер до judge.

**Приёмка.** Ручная разметка 50 случайных задач: совпадение метки ≥ 95%.

### P1.2 Убрать «SQL-вопросы» и сырые коды меты

**Проблема.** 25 из 93 вопросов опираются на сырые коды: «регионы с кодами
24 и 6», «регионах с буквой „В" в названии», «код ОКПД2 27.9» без расшифровки.
Так не спрашивает пользователь; модель учится матчить фасетный заголовок, а не
искать по содержанию. Плюс грамматические ляпы («Красноярская область»,
«Белгородский регион»).

**Действия.**
- В промпте композитора запретить: коды регионов, «с буквой X в названии»,
  голые коды ОКПД2 (код допустим только вместе с человекочитаемым названием
  категории).
- Маппинг `region_code → region`, `okpd2_code → название категории` делать до
  промпта (словарь категорий ОКПД2 верхнего уровня — в `arqg/zakupki/`).
- Линтер вопросов: регэксп на «кодом \d», «с буквой», «регион \d» → repair.
- Проверка названий регионов против меты (край/область/республика) — дешёвый
  словарный чек.

**Приёмка.** 0 вопросов с сырыми кодами в финальном пуле; 0 ошибок в типе
субъекта федерации.

### P1.3 Снизить шаблонность вопросов и однообразие полей ответа

**Проблема.** 32/93 вопросов начинаются с «какая из (двух) закупок…», 34
упоминают ЕИС; ~80% вопросов сводятся к двум полям ответа — дата размещения
или НМЦК. `export.dedup_threshold: 0.8` такие шаблоны не ловит.

**Действия.**
- В 1-of-N отбор (`gates.py::_pick_batch_winners`, `batch_selection: datamix`)
  добавить штраф за n-gram/шаблонное сходство с уже принятыми вопросами
  (не только за бин fused_gap).
- Расширить пул `answer_field`: заказчик, предмет закупки, размер обеспечения
  заявки, число позиций, способ определения поставщика, победитель (где есть).
  Квоту на поле ответа — в конфиг (например, ≤ 30% на одно поле).
- В промпт композитора — набор стилевых регистров (канцелярский, разговорный,
  телеграфный) с ротацией.

**Приёмка.** Ни один префикс-шаблон > 20% пула; ни одно поле ответа > 30%;
доля вопросов со словом «ЕИС» < 20%.

### P1.4 Ответы-идентификаторы

**Проблема.** 17 ответов — анонимизированные `pn_lot_*` вперемешку с
реальными номерами (`0317100000521000022`): анонимизация корпуса
неконсистентна, а «pn_lot_2933013» как ответ неестественен.

**Действия.**
- В `scripts/build_zakupki_corpus.py` — единая схема номеров (либо все
  реальные, либо все синтетические, но правдоподобного формата
  19-значного номера ЕИС).
- Для вопросов, где ответ — номер закупки, требовать в вопросе явное «укажите
  номер(а) закупок» (в v3 это уже почти так — закрепить проверкой).

## P2 — профиль сложности, окружение, масштаб

### P2.1 Оживить verbatim_lookup

**Проблема.** G_VERBATIM отсёк 16/16 кандидатов, почти все — по
`dense_already_finds_entry`: фасетный заголовок в пассаже делает dense-ветку
сильной, асимметрия ветвей (lex легко / dense мимо) на zakupki не выполняется.
Механика «выбор инструмента» в датасете отсутствует.

**Действия.**
- Строить verbatim-задачи от идентификаторов, НЕ входящих в фасетный
  заголовок пассажа: `purchase_number` / `customer_inn` сейчас сознательно
  исключены из фасетов (см. комментарий в конфиге) — использовать их как
  verbatim-якорь, который dense-ветка не видит.
- Либо откалибровать пороги `verbatim_lex_gap_max` / `verbatim_dense_gap_min`
  по фактическому распределению gap'ов zakupki (в v3 они с ckr).

**Приёмка.** `verbatim_lookup` даёт ≥ 5% задач пула, G_VERBATIM pass_rate > 0.

### P2.2 Донасытить окружение дистракторами

**Проблема.** Инъекции только у 31% задач; у 55% пустая L2-полоса
(`share_tasks_with_empty_L2_band: 0.55` при `min_l2: 2`);
`share_L3_alarm: true` (10.9% > 10%). Для agentic-RL плотность near-miss'ов
важнее числа задач.

**Действия.**
- Увеличить `distractors.l2_pool` (20 → 60) и `l1_pool`; на tiny-корпусе
  полоса пуста физически — на полном корпусе перепроверить и тюнить уже там.
- Разобрать причины отклонений в `injection_ledger.jsonl` (rejected-счётчики
  по типам) и ослабить лишние фильтры, если полоса пустеет из-за них, а не
  из-за корпуса.
- Если L2 не набирается — генерировать L3 до квоты, но держать
  `share_L3 ≤ 10%` (алярм уже есть).

**Приёмка.** `share_tasks_with_empty_L2_band < 0.2`, `share_L3_alarm: false`,
`share_tasks_with_injection ≥ 0.6`.

### P2.3 Выровнять профиль сложности

**Проблема.** hop_depth = 2 у 89% задач (3+ хопа — 10 шт.); fused_gap
перекошен: low-бин 14% при цели 30%; 98.5% fact-групп — синглтоны.

**Действия.**
- Поднять `taxonomy.candidates_per_cell` до плановых 6 — datamix-отбору
  нужен выбор, чтобы заполнять недобранный low-бин.
- Добавить квоту на hop_depth в отбор победителей (аналогично бинам
  fused_gap).
- Для fact-групп > 1 нужны документы с дублирующими фактами — проверить на
  полном корпусе; на tiny это ожидаемо вырождено.

**Приёмка.** `fused_gap_share` в пределах ±5 п.п. от таргета по всем бинам;
доля hop_depth ≥ 3 — не менее 20%.

### P2.4 Масштаб для валидации + гигиена

**Проблема.** Holdout 18 задач — шаг метрики 5.6%, сравнение моделей
бессмысленно. Все задачи помечены `corpus: "ckr"` / `task_id: syn_ru_ckr_*`,
хотя это zakupki (запуск шёл со старым `corpus_name`). Density-медиана
provisional (`n_reach_tasks: 93 < 300`).

**Действия.**
- Финальную генерацию — на полном корпусе zakupki; цель
  `export.holdout_size: 300` в конфиге уже стоит, tiny её физически не даёт.
- Перегенерировать с `corpus_name: zakupki` (в текущем конфиге уже исправлено;
  v3-артефакты либо перегенерить, либо переименовать скриптом).
- Holdout дополнительно прогнать через ручную выборочную проверку
  (≥ 50 задач) перед использованием как эталона.

**Приёмка.** Holdout ≥ 300 задач; `n_reach_tasks ≥ 300`
(`reach_median_is_working: true`); `corpus`-метка и префикс `task_id`
соответствуют корпусу.

## Порядок работ

| Этап | Пункты | Зависимости | Результат |
|------|--------|-------------|-----------|
| 1 | P0.4 | — | очищенный train v3, отчёт об отсеве |
| 2 | P0.1, P0.2 | — | completeness на всех механиках, механические ответы |
| 3 | P0.3, P1.1, P1.2 | 2 | независимый judge, честные метки, естественные формулировки |
| 4 | P1.3, P1.4, P2.1 | 3 | разнообразие шаблонов/полей, живой verbatim_lookup |
| 5 | тестовый прогон на tiny | 2–4 | все критерии приёмки P0–P1 зелёные |
| 6 | P2.2, P2.3, P2.4 — прогон на полном корпусе | 5 | train + holdout ≥ 300, финальный аудит |

Каждый этап заканчивается прогоном `scripts/audit_sid_answers.py` (P0.4) —
он же становится постоянным пост-экспорт линтером пайплайна.
